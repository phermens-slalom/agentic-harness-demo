All milestones

The value of each one

The codes at the foot of each card are the backlog items. They are explained in the glossary.

M0DONE

Make the gate trustworthy

Value
The merge gate can be relied on. It stops when evidence is missing, notices an agent cheating on its own tests, and always asks people to review the files that control the rules.
Where it is
Finished on 18 November. Nothing further planned.

H0, G1 to G7

M1WAITING ON A DECISION

Real GitHub, enforced

Value
The harness stops being a demo against fakes. It works on real GitHub issues and pull requests, and GitHub itself refuses to merge a change the gate says needs people.
Where it is
The Copilot setup for generated repos is done. Everything else waits on how the harness is allowed to ask Copilot for work.
Waiting on
A security team decision: GitHub says Copilot assignment needs a user token, and the harness rule allows only installation tokens (R2).

S4 done · R2, R1, R7 waiting

M2WAITING ON M1

Durable, controllable runtime

Value
The harness can run on its own. Approvals survive a restart, a repeated webhook cannot start duplicate work, and someone can pause it or cap what it spends.
Where it is
The AI roles now return checked answers, retry once and stop safely. The hosted runtime, queue and kill switch come after real GitHub.
Waiting on
Real GitHub (M1), and a hosting decision from the platform team (Q5).

R6 done · R3, R4, R5 waiting

M3MOSTLY DONE

Security: use what exists

Value
Known security tools do the scanning, and the harness adds only what is specific to it. New models, hosts, regions, data stores and dependencies get extra approvers instead of slipping through.
Where it is
Secret and code scanning in CI, new-capability detection and the Model Armor input scanner are in. Model Armor has run on a fixture only.
Waiting on
Protecting the harness repo itself needs M1. The builder residency check needs real GitHub. GitHub lists Copilot data residency in the US and EU only, so Australian use is a security team call (Q3).

S1 to S3 done · S5, D1 waiting

M4LATER

Observability and audit

Value
Anyone can see why a decision was made, without secrets in the record. The evidence also lets us decide, on facts, when the gate can be trusted with more.
Where it is
Not started. It follows the durable runtime.
Waiting on
The durable runtime (M2).

O1 to O3

M5IN PROGRESS

Evals that measure agents

Value
We can show how good a generated agent actually is, not only that its checks ran, and a change cannot make it worse without someone noticing.
Where it is
Coverage and quality are now required checks, a safe first-pass scan runs before anything else, and the starter pass mark is 80%. A comparison against an accepted baseline is written but not switched on.
Waiting on
An accepted baseline, an approved evaluation project, region and identity, and a design that keeps hidden test cases hidden (Q18). Live replay also needs pilot repositories.

E3 in progress · E1 blocked · E2 later

M6LATER

Golden-workflow coverage

Value
The harness helps with more of the eight stages: checks for infrastructure changes, reuse of an existing reference template, a release review pack, registration and approvals inside GitHub.
Where it is
Not started. Lower priority than the pilot.
Waiting on
Access to the reference template (W2).

W1 to W5

M7IN PROGRESS

Hygiene

Value
The repo stays easy to work in. Formatting, spelling and docs links are now checked on every change.
Where it is
Last piece: run the end-to-end script in CI on Linux and Windows.

H1 in progress

M8IN PROGRESS

Generated agent ready for the pilot

Value
A team can pick up a freshly generated agent, run its checks without cloud access, see an allowed and a refused action, read a redacted diagnostic, and know what needs approval before going live.
Where it is
The starter agent is read-only, reports redacted diagnostics and carries one pinned skill. Next is a preflight command and an end-to-end acceptance test (H2). Two live runs are still to do.
Waiting on
Approved non-production cloud setup for the live runs.

A2 done · H2 next · A1, A3 awaiting live runs · E3

M9NEXT

Agent intake and authoring

Value
A person who owns a business problem can ask for an agent with a form, answer plain-language questions, and get a tested, governed pull request without writing Python. People still approve everything.
Where it is
The request form and an offline parser that turns it into an untrusted draft are done. Next: a fixed library of approved connectors, then a prototype that asks the questions, then agent authoring. All offline, against fakes.
Waiting on
The hosted version needs real GitHub and the runtime (M1, M2), a hosting route and an owner for who sponsors a request (Q17).

I1 done · I2 next · I3 to I6 · I7 blocked

M10WAITING

Delivery process

Value
A clear path from idea to production in lanes, with exit requirements the controls enforce, so different kinds of people know what to do next and what must be true before work moves on.
Where it is
The documentation is done: the two layers, who runs the process, the lanes, demo-ready and MVP-ready, the roles and what enforces each exit today. Next, as follow-up work: the lanes and standards as policy data, a lane command, a spec-gap skill, a lane-exit contract an orchestrator can call, and the RACI change.
Waiting on
Who the security reviewers are and the escalation process (Q19), whether the lanes and the lane-aware RACI proposal stand and who owns the process (Q20), where long human waits live (Q21), and who owns the standards register (Q23).

DP1 done · DP2, DP3, DP6, DP7 todo · DP8, DP10 blocked

M11LATER

Platform scope

Value
The system is a full multi-agent platform, not small experimental agents. This covers the pieces beyond one agent’s code: a multi-agent template, agent identity, and how agents are invoked at runtime.
Where it is
Planned only. Google services and the connector library are covered elsewhere (M2, M3, M9).
Waiting on
How agents are invoked at runtime (Q22), which identity system applies and who owns it, and the security reviewers (Q19).

DP4, DP5 todo · DP11 blocked

M12LATER

Pilot on real work

Value
We learn whether the lanes and controls work on a real piece of work, not only on paper. The draft success criteria still need an owner to agree them.
Where it is
Not started. It comes after the delivery process, the platform scope and live evals.
Waiting on
M10, M11, live evals (E3), and owner agreement on the success criteria (Q19, Q20).

DP9 blocked
