Core ideas

TermPlain English
HarnessThis repo. It wraps AI agents in rules, checks and approvals so that they can build software safely.
AgentAn AI program that can use tools and make choices. The harness has agents that plan and review. The generated agent repos hold the agents that the app teams build.
Generated agent / agent repoA new repo the harness creates from agent-template/ for one agent.
Golden workflowThe harness's standard path for taking an agent live. It has eight stages: frame, register, provision, connect, build, verify, release, operate. Defined in policy/golden_workflow.yaml.
StageOne step of the golden workflow.
Onboarding steps (13)The 13 example steps in the adaptable RACI configuration. The eight stages group them.
Issue-to-merge loopThe part of the harness that turns a GitHub issue into a merged change. It covers the Build and Verify stages only.
Build stage / Verify stageBuild: an agent writes the change. Verify: checks and a review decide if it can merge.
Mission BriefA short document that states what an agent is for, who uses it, what data it uses and which hosts it calls. Its test ideas become eval criteria.
Opportunity CanvasDrafted in the Frame stage. To be validated: what it contains.
RunbookA how-to-operate guide for one agent: what it does, how to spot faults, how to roll back.
Spec (spec.yaml)A small file with the facts the bootstrap needs: name, division, owner, sponsor, classification, description, and optional location, environments and egress hosts.
DivisionThe business area that owns an agent.
ClassificationA label for how sensitive an agent is. To be validated: the list of values; the example uses internal.
SponsorThe business person who backs an agent.
Egress hostA website or service that an agent is allowed to call out to. The spec lists exact host names only.
Registry entryA record for each allowed egress host in the Agent Registry.
Landing zoneThe ready-made cloud setup that new projects are placed in. Referred to for WIF and for provisioning.
ProvisionCreate the cloud project and its settings for an agent.
Residency (data residency)Keeping data and AI processing inside allowed places. Here: Australian regions only.
Allowed regionsaustralia-southeast1 (Sydney) and australia-southeast2 (Melbourne), listed in policy/residency.yaml.
Global endpointA cloud address with no fixed location. Never allowed.
PhaseHow much the gate trusts itself. Phase 1: a person reviews every agent PR. Phases 3 and 4: the lowest-risk changes may merge by themselves. The file ships at phase 1.
TierHow risky a change is. Tier 1 is low (tests and docs). Tier 2 is the default. Tier 3 is high (controls, Terraform, IAM, production, sensitive areas, agent instructions).
Required checksSix automatic checks every agent PR must pass: lint, tests, coverage, quality, evals_no_regression, secret_scan.
LintAn automatic style and error check on code.
EvalsTests of how an AI behaves (not just whether code runs).
Golden taskA saved example case used to test the harness. It says what the right outcome is.
Delivery processThe path a person follows from idea to production, in lanes, with exit requirements. It sits on top of the harness. Proposed; see DELIVERY.md.
LaneA phase of the delivery process: prototype, verify, harden or operate. Each has exit requirements. A lane never switches off a deterministic control.
Exit requirementWhat must be true before work leaves a lane. Each one is enforced by an existing control, or marked Not built with its roadmap ID.
Golden data setIn a generated agent: the cases that verification judges the agent against (the same idea as the golden set, used as a lane exit). Not the harness's own golden tasks.
Demo-readyThe Prototype exit: the agent runs in the sandbox against synthetic data, works through the main cases of the drafted golden data set, and the hypotheses are visible. A recorded demo is the evidence. Not secure, reviewed or connected to real systems.
MVPA minimum viable product. In the delivery process, MVP-ready is the Verify exit: golden data set and evals pass with no regression, coverage and quality are met, the review checklist is clean, and the agents meet their success criteria in the intended non-production environment. MVP-ready is what starts Harden, where formal security work happens (proposed).
PersonaA kind of person who works with the harness and delivery process, described by role: product manager, application engineer, AI governance, security or platform. See PERSONAS.md.
Golden setIn a generated agent: example cases for the agent's own behaviour.
BaselineThe last accepted eval results. A new PR may not do worse than it.
ThresholdA pass mark for an eval. The business owner sets it, not the builders.
HoldoutSecret test cases the coding agent never sees. Described in the template; the runner is still to be built (E3).
AgentRequestA GitHub issue, raised with the issue form, that asks for a new agent. The harness turns it into an untrusted draft (a Mission Brief, a review-only spec and a list of missing fields). A draft grants nothing.
Intake agentPlanned (M9). An agent that would interview the requester on the issue and open a PR for the agent they need. It only raises PRs and never approves or merges.
Connector libraryPlanned (I2). A fixed, reviewed set of ways for generated agents to reach other systems. Anything outside it goes to a person.
PreflightThe first job in a generated repo's checks. It inspects a candidate checkout without running it, using trusted code from the base revision. A tripwire, not a sandbox.
Coverage / QualityTwo required checks in generated repos. Coverage enforces a minimum share of agent code run by tests (80% to start). Quality runs the style, complexity and type checks.
Dry-run evalAn eval that uses scripted fakes. It is free and fast.
Live evalAn eval that calls real models. It costs money and needs approved cloud access. Not built yet.
TraceA step-by-step log of what the harness did on one task.
EscalateStop and hand the task to a person.
Plan approvalA person approves the plan before the builder starts.
SkillA text file of guidance that changes how an agent behaves. It does not give the agent any new powers.
pinned skills repositoryThe configured source of approved skills. The harness does not copy skills in; it reads a pinned checkout.
Skills lockpolicy/skills.lock.yaml: the exact approved version and fingerprint of each skill. Empty today.
PinningLocking to one exact version so nothing changes without a reviewed PR.
TODO(owner)A marker for a decision that needs an accountable role or owner. Do not guess; keep it unresolved until assigned.

The gate and its outcomes

The merge gate (merge_gate.py) is plain code. It never calls an LLM.

OutcomePlain English
auto_mergeThe change may merge without a person. Only for tier 1, only at phase 3 or 4, and only if nothing new was detected.
human_approvalA named set of people must approve before it merges.
reject_to_planningThe change is too big (over 400 lines). Split it and plan again.
escalatedSomething is wrong or unknown (failed or missing check, tampering, a blocked input). A person must look.
ignoredThe issue has no agent:* label, so the harness does nothing.
TermPlain English
Fail closedWhen unsure, stop. Missing evidence counts as a failure, never as a pass.
Reviewer lockoutThe agent that built a change cannot approve it.
Harness controlsFiles that control the gate or agent behaviour (workflows, CODEOWNERS, policy, skills, prompts, eval thresholds). Always tier 3, never auto-merged.
Privileged YAMLConfig files that grant access. To be validated: which files count (Q1).
Tamper checkLooks at a change for signs the agent weakened its own tests or evals (deleted tests, added skips, lowered thresholds).
Capability checkLooks at a change for newly added models, hosts, regions, data stores, dependencies or tool and protocol links. It adds approvers. It never approves or blocks by itself.
ApproversThe roles that must sign off. The gate works them out from the changed file paths.

Safety words

TermPlain English
Input guardA scan of untrusted text before an LLM reads it. Ships in shadow mode.
Shadow modeRecord what would have been blocked, but let the task continue. Used while we learn about false alarms.
Enforce modeA match, crash or incomplete scan stops the task.
Prompt injectionText that tries to give an AI new orders (for example "ignore previous instructions").
SunglassesThe pattern-matching scanner used by the input guard. A cheap tripwire, not a full defence.
Model ArmorA Google Cloud service that screens prompts and replies for prompt injection and other risks. The main scanner (S2). Wired in and tested with a fixture. Not run against the live service yet.
Composite scannerRuns Model Armor and Sunglasses on the same text. Blocked if either blocks. A scanner that errors counts as a block.
ModelArmorPluginThe part of ADK that screens a model's input and replies with Model Armor. Registered on the harness's own ADK app.
Template (Model Armor)A saved set of Model Armor settings in one cloud region. Not the same as agent-template/.
Adversarial taskA golden task that tries bad behaviour to prove the harness catches it.
Known gapA documented miss. It is reported as open and must be removed once it is fixed.
Reward hackingAn agent passing its checks by cheating (for example by editing the tests) rather than by doing the work.
GitleaksA tool that finds secrets (keys, passwords) in code. Used in CI.
zizmorA tool that checks GitHub workflow files for security mistakes.
CodeQL / dependency reviewGitHub code-scanning and dependency checks. They run on public repos or when GHAS_ENABLED=true.
SecretA password, key or token. Never kept in code, traces or audit records.
GitHub AppThe way the harness acts on GitHub. No personal access tokens.
Least privilegeGive only the access that is needed and no more.

Parts of the code

TermPlain English
PortA named slot in the code (such as GitHubPort) that real or fake parts plug into. Lets the workflow stay the same when parts change.
AdapterA real part that plugs into a port (for example the ADK agents or the Copilot builder).
FakeA scripted stand-in used in tests and dry-run evals. No network.
BuilderThe part that writes the code change. Default: GitHub Copilot.
Triager / Planner / ReviewerThe three LLM roles: size the issue, write the plan, review the result.
Repo contextAGENTS.md, the file tree and a few named files, read-only, size-capped and scanned, given to the planner and reviewer.
BootstrapThe agentic-bootstrap command with three stages: new (make an agent repo), check (harness policy checks), plan (the ordered PRs for a cloud project).
Template (agent-template/)The starting repo that new copies for each agent.
SandboxAn optional, not-yet-built way to run a build in a Cloud Run Job. Not the default.
e2e scriptscripts/e2e.py: runs the harness end to end, then cleans up.
agents-cliGoogle's command-line tool for agent projects (lint, evals, scaffold, deploy).
uvA Python tool for installs and environments.
PydanticA Python library that checks data has the right shape.
HypothesisA Python library that tests rules across many generated inputs (property tests).
ty / ruff / codespellType checker, style checker and spell checker.

Roadmap codes

The roadmap (ROADMAP.md) numbers its work. Each code is stable.

CodePlain English
D-01 … D-17Decisions. Short design choices with a reason and an owner. See DECISIONS.md.
Q1 … Q23Open questions for this project. See OPEN_QUESTIONS.md.
M0 … M12Milestones (groups of work). M0 makes the gate trustworthy; M8 gets a generated agent ready for the pilot; M9 lets a person request an agent and get a governed PR; M10 builds the delivery process, M11 the platform scope, and M12 pilots them on real work.
H0 to H2Hygiene items: the repo guide (H0), CI and repo tidy-up (H1), and the generated-project preflight and acceptance test (H2).
G1 … G7Gate items: fail closed, control files in tier 3, tamper detection, plan approval, path matching, least-privilege CI, policy validation.
R1 … R7Runtime items: GitHub checks and CODEOWNERS, real GitHub client, durable workflow, ingress queue, controls, hardened ADK adapters, reviewer sees the diff.
S1 … S5Security items: scanners, Model Armor, new-capability detectors, Copilot environment, supply chain.
D1Builder residency (not the same as the D- decisions).
O1 … O3Observability: traces and audit, metrics, shadow gate and phase promotion.
E1 … E3Evals: live replay, reviewer defects, real template evals.
W1 … W5Workflow coverage: workload PR checks, template from existing reference agent template, release pack, registration, GitHub-native human gate.
A1 … A3Generated-agent items: authorisation boundary, telemetry, governed skill.
DP1 … DP11Delivery-process items in M10 to M12: this documentation (DP1), lane and standards policy files, the lane CLI, a spec-gap skill, the E2 priority change, the D-16 policy change, the lane-exit contract, a multi-agent template variant, identity integration, the runtime invocation contract, and the pilot. Not the same as the P0 / P1 / P2 priorities.
I1 … I7Agent intake items: request form and parser, connector library, intake agent, authoring, cross-model review, tailoring through comments, hosted trigger.
Status wordstodo, doing, blocked, review, done, dropped.
P0 / P1 / P2Priority: before the agent discussion, before the pilot agent, after the pilot.
S / M / L (size)Up to half a day, up to two days, more than two days.

Roadmap codes such as R2 or I1 are explained in the last section. See the roadmap for what each milestone is worth.
